Canonical current-state snapshot for getpromonight.com. This file is the source of truth for site state across every thread in the project. When a thread needs current numbers, it reads here first, then pulls anything live from PostHog in-thread.

## How to use this file

- Treat this as authoritative over scattered older memories. If a number here conflicts with something half-remembered from an old chat, this wins.
- The fast-moving traffic numbers below are a baseline, not real-time. Any thread can pull fresher PostHog figures live; this file holds the last clean read plus the slow-moving structural state.
- Field tags: [LIVE] pulled in-thread from PostHog or a fresh export, [AUTO] generated by the Claude Code audit script from repo + Firestore, [MANUAL] supplied by Matt. Sections still on last-known values are flagged STALE with the date they were last confirmed.
- Regen cadence: weekly. Re-run the audit script, re-upload this file to project knowledge to replace the prior version. Generation can be automated; the project-knowledge upload is the one manual step that makes it visible to every thread.

### MEASUREMENT BOUNDARY: /team-rankings was invisible to crawlers [MANUAL, added 2026-08-21]

- **2026-08-21 is a hard discontinuity for /team-rankings, and any historical GSC read on that URL is not comparable to anything after it.** Until merge faddf1d the page served **zero** of its 75 ranked rows to crawlers. Google received the hero, the capsule, the FAQ and the JSON-LD, but not the ranking, which is the page's entire reason to exist. If that URL has never ranked for a team-ranking query, this is why, and its search performance from today is a NEW SERIES rather than a continuation. Impressions, average position and CTR before today measured a page whose content Google could not see.
- MEASURED, not inferred, with cache-busting curls on 2026-08-21: `/team-rankings` served 255,556 bytes and **0** rows; its sibling `/best-promos` served 682,809 bytes and 50; `/best-promos/bobbleheads` served 50; `/teams` served its grid. After the fix `/team-rankings` serves 331,303 bytes and **75** rows.
- CAUSE. `TeamRankingsList` called `useSearchParams` at its top level to read `?league=`, and the page wrapped the whole list in one `Suspense` boundary. A client component calling that hook opts out of static prerendering, so the boundary's entire subtree was replaced by BAILOUT_TO_CLIENT_SIDE_RENDERING in the served HTML and hydrated only in a browser. The page looked perfect to every human who ever opened it.
- HOW LONG. Since the page launched. There is no window during which it served rows; the pattern was present from the component's first commit.
- THE CLASS MATTERS MORE THAN THE INSTANCE, which is why this is filed as known-issues entry 33 rather than a one-line fix note. Three components had already been quarantined correctly against this exact trap, TWO OF THEM CARRYING COMMENTS EXPLAINING IT, and a fourth still shipped with the bug. The failure is silent in every place a defect is normally caught: the build succeeds, the type check passes, the test suite passes, and a browser renders it correctly, because a browser runs the hydration a crawler does not. A convention that lives only in comments is invisible at the moment a new component is written.
- TWO FAILURE MODES, DIFFERENT CHECKS. Mode 1 is content missing from served HTML, caught by a row count in a curl. Mode 2 is content DUPLICATED after hydration, which the curl cannot see because the served HTML is correct. Both are now runnable commands, documented in entry 33: the curl for mode 1, and `scripts/check-hydration-duplicates.js` for mode 2, which exits non-zero on any hidden duplicate so it gates rather than reports.
- ENFORCEMENT. `src/lib/__tests__/search-params-bailout.test.ts` fails the build on a new `useSearchParams` caller that neither renders null nor owns its own boundary, on a page directly wrapping a self-bounded component in `Suspense`, on a self-bounded component losing its boundary or its reader, and on reintroduction of the URL-synced chip mode. Verified capable of failing, not just of passing. It does NOT catch a boundary further up the tree, and entry 33 says so; that shape still needs a human.
- ALSO CORRECTED IN THE SAME MERGE, both live before today: ScoreBadge told assistive technology that team scores were "out of 100" when the scale is unbounded and the top team sits at 162, wrong on 16 of 75 rows and, being the accessible name, the only version a screen-reader user received. And the team-rankings FAQ contradicted the shipped scorer on the variety bonus cap (3/8/15, not "caps at 8"), on the composite formula (total promo score over home games times 1.5, not average promo score), and on the hot-promo cap (10 highlighted promos, not 16), in page text and in FAQPage structured data.

### A/B/C SERP diagnostic protocol (STANDING METHOD)

The zero-CTR-at-good-position signature (e.g. Red Sox "promotional schedule" position 6.3, 87 impressions, 0 clicks) means the worst pages are not a snippet problem. A title rewrite cannot fix a click that a SERP feature or competitor is intercepting. Before any further rewrite, classify each stuck team's top 2-3 giveaway queries in a fresh incognito US Google window:

- Bucket A, competitor or feature owns the visible fold (MLB.com with sitelinks, ticket carousel, events pack). Signature: good GSC position, near-zero CTR, query matches official MLB.com content. Fix: not a rewrite. Earn a SERP feature with structured data, or deprioritize.
- Bucket B, answer shown in place (featured snippet or AI Overview). Signature: zero CTR across the whole organic block, factual list query. Fix: try to become the featured snippet, or concede.
- Bucket C, your result is visible and clickable but unappealing. Signature: decent position, low-but-nonzero CTR, no dominant feature. Fix: title/snippet rewrite. This is the only bucket a rewrite addresses.

Action rule: rewrite only C's, attempt feature capture on B's, route A's to authority work or drop. Study what the Cubs/Tigers/Orioles titles do (genuine winnable C-bucket pages) and port the pattern to other C teams.

## 8. Absent-write monitoring gap [MANUAL, added 2026-08-18]

The scoring freeze exposed a structural asymmetry: the scanner framework has strong guards against BAD writes (hash-skip, absent-streak tombstone threshold, recurring floor-guard, snapshot-first reversibility, hold alerting) and none against ABSENT writes. A subsystem that silently stops writing looks identical to a quiet week: every surface kept serving, every honest stamp kept showing its stale value, and the only tell was a timestamp age nobody watches. teamScores sat frozen for 56 days while two indexed surfaces claimed weekly updates, and the freeze was found by a copy audit, not an alarm.

Nothing watches stored timestamp age today. Known stale-with-no-alarm stamps as of 2026-08-18:
- appConfig/dataVersion.lastDataUpdate = 2026-06-23T02:01:14.999Z (tracks the last scoring run of the pre-freeze era; nothing in src reads it and nothing refreshes it)
- metadata/lastUpdated.timestamp = 2026-03-30T22:01:34.713Z (141+ days old; writer unknown or retired)
Both predate the rescore and were deliberately not touched by it; recorded here as known-stale rather than silently trusted. The existing weekly staleness-check workflow did not catch the freeze: whatever it covers, it does not alarm on teamScores.computedAt or on these metadata stamps.

Fix shape when picked up: a timestamp-age tripwire, most naturally hosted in the existing staleness-check workflow, asserting teamScores max computedAt is younger than 8 days during each scored league's season, plus a decision per orphaned stamp (wire it to a real writer or delete it). Until then, treat any stored timestamp on a surface or in appConfig as unverified until its writer is identified.

### Hub stat bar "N promos tracked" [MANUAL, added 2026-08-21]

**Recorded here with a correction to the framing it arrived with.** This surface was raised
as a third known-stale stamp alongside the two above. It is not stale, and calling it stale
would put a false claim in this file. The defect is real but it is a different one.

**What it reads.** `getLeagueHubStats` (`src/lib/data.ts:1296-1313`) sums `promoCount` across
`teamScores` docs for the league. `HubStatBar` (`src/components/hub/HubStatBar.tsx:18-35`)
renders it as "{N} {league} promos tracked" plus "avg promos per team", on `/mlb`, `/wnba`
and `/mls`.

**What it reads TODAY**, measured 2026-08-21:

| league | rendered total | rendered avg per team |
|---|---|---|
| MLB | 2,577 | 85.9 |
| MLS | 413 | 13.8 |
| WNBA | 236 | 15.7 |

**Why it is not a staleness entry.** `teamScores.computedAt` spans 2026-08-18 to
**2026-08-20**, one day old at the time of writing. The scoring writer is live again after
the rescore, so this surface is being recomputed, not frozen. It does not belong in the list
above.

**What is actually wrong with it.** Those three totals match the ALL-TIME visible promo
counts in Firestore exactly (MLB 2,577, MLS 413, WNBA 236). `teamScores.promoCount` is a
lifetime tally, so the hub bar is the same class of defect as the team-page counts fixed on
2026-08-21 in `fix/promo-count-derivation`, in a different pipeline. Being freshly computed
makes it worse rather than better: it will keep being recomputed as a lifetime figure
indefinitely.

**Why converting it to allTimeCounts would be the wrong fix.** It would change the source
without changing the meaning, and it would cost 30 team reads per hub render to arrive at the
number the surface already has. The question is not where the number comes from, it is what
the label should promise. "Promos tracked" is defensible for a lifetime dataset figure and
should then say so explicitly. "Avg promos per team" is not defensible as a lifetime average
next to a hub whose purpose is what is on this week. Decide the label first, then the source.

**Not fixed now, deliberately.** No user-facing claim here is false in the way the team-page
counts were, because "tracked" can honestly describe an archive.
